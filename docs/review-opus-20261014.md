# rview の Opus レビュー（2026-10-14 JST）

**結論**
1. 人間が画像を目で選ぶための道具として、小さく、よくできている。直す所はほぼ無い。
2. いちばん大きな見落としは「人間の評価（+2〜-2 と f/g への振り分け）が、どこにも使われていない」こと。二軍の画像の改善ループにとって、これが一番安い「正解」のデータになる。
3. 新しい機能は足さなくてよい。凍結に近い「使う道具」として残す。

## 指摘（重要な順）

1. **評価の記録が下流に流れていない（見落とし）** — 残す＋つなぐ（手間：小、相手側の作業）
   各フォルダの `rview-ratings.jsonl` と、`<フォルダ>f`・`<フォルダ>g` への移動は、人間が実際に「良い・悪い」と決めた結果である。今のところ、これを読む repo は無い。二軍の画像の改善ループ（プロンプトを直して品質を上げる繰り返し）を作るときに、「人間が残した絵／消した絵」を正解の例として読む入口を、ループの側に1つ作るとよい。rview 側は今の形式（1行1件、最後の行が今の評価）のままで足りる。形式を変えない。

2. **README の先頭が、メモリの予算の細かい説明で始まっている** — 直す（手間：極小、急がない）
   利用者が最初に知りたいのは「起動のしかた」と「キー操作」。先読みの予算の説明（20行ほど）は SPEC か後ろの節へ回してよい。人間の目の負担を考えると、先頭は短い方がよい。

3. **2つの起動の形（デスクトップと Flask）が API を別々に持っている** — 残す（手間：—）
   `local/rview.py` と `remote/server.py` は似た処理をそれぞれ持つが、ファイル操作の肝（お気に入りの移動・評価の記録・パスの境界）は `rview_media.py` に1つにまとめてある。重複は見た目より小さい。今は統合しない（利点より壊す危険の方が大きい）。

4. **試験の量は機能に見合っている** — 残す
   試験はブラウザの操作・お気に入りの衝突・パスの境界と、利用者が困る所に向いている。監査のための層は無い。過剰な作りの心配は無い。

5. **お気に入りの古い重複の掃除（`scripts/dedupe_favorites.py`）** — 残す（一回きりの道具）
   比べ方は全体の規則（サイズ → 先頭 1MB → ハッシュ）どおり。台帳は repo の外。もう使い終わっていれば、次の整理のときに消してよい。

## 残すべき良い所
- 「お気に入り＝隣のフォルダへの移動」「同じ中身なら元を消す、違えば番号を付ける」という、人間の作業の型に合った単純な規則。
- 画像の中身を Git に入れない、データは repo の外、という線引き。
- 起動の既定がループバックで、外へ開くときは明示が要ること。
